# progress-panel 0.2 仕様書：利用枠・コンテキストメーター

## 目的

goal2 で長い作業を任せたり、サブエージェントを何体も同時に動かしたりすると、気づかないうちに利用枠やコンテキストを使い切りがちです。その手前で気づけるよう、今の progress-panel に次の機能を足します。

- 画面下のステータス行に、利用枠とコンテキストの使用率を常に出す
- 決まった段階を超えたときに一度だけ知らせる
- 消費のペースが早いときは、その状態のあいだ表示し続ける

新しい mod は作らず、progress-panel を拡張します。ステータス行は1つの mod につき1本までなので、既存の「作業中 1/3・…」の行に続けて出します。

## データの出どころ

| 値 | 取り方 |
| --- | --- |
| 利用枠（`five_hour`、`seven_day`、ほか） | `session.measure` イベントの `rateLimits`（`percentUsed`、`resetsAt`） |
| コンテキスト | `session.measure` の `context.percent`（モデルのコンテキスト長に対する割合）と `tokens`・`window` |
| 起動直後の値 | `session.start` で `$.session.usage()` を一度読む |

前提と制約：

- 利用枠の数値は「このセッションが最後に受け取った API 応答」時点のものです。ほかのセッションや claude.ai で使った分は、次の応答まで反映されません。そのためパネルには、値を取得した時刻を出します。
- サブスクリプション以外（API キーなど）では `rateLimits` が空になります。その場合、利用枠の表示は丸ごと省きます。
- `/compact` の直後は、次の応答まで `context.percent` がありません。値が届かないあいだは、直前の値を残さず「—」とします。
- `session.measure` が呼ばれるのは、メインスレッドのターンが終わったときと、利用枠が1ポイント動いたときです。

## ステータス行

既存の要約の後ろに ` ｜ ` で区切ってつなげます。

```
作業中 1/3・コマンドを実行中 ｜ 5時間 62%（18:40 回復）・週 35%・文脈 45%▲
```

- **5時間枠**：`5時間 NN%（HH:MM 回復）`
  - 80%以上なら先頭に `⚠` を付けます。
  - ペースが早いときは `（18:40 回復・17:55頃に上限）` のように、上限に達する予測時刻を添えます。
  - 回復時刻を過ぎていれば `5時間 回復済み` と出します（次の応答で更新されます）。
- **週枠**：`週 NN%`
  - 80%以上なら `⚠` を付け、`（10/22 回復）` のように回復日を添えます。
  - ペースが早いときは `（ペース速め）` を添えます。
- **知らない種類の枠**（ゲートウェイの `spend_limit` など）：`kind NN%` と汎用の形で出します。
- **コンテキスト**：`文脈 NN%`
  - 40%以上で `▲`、50%以上で `⚠`、60%以上で `‼` を付けます。
- 利用枠もコンテキストも値がなければ、区切りごと出しません（今の表示のままになります）。

## 通知（トースト）

| きっかけ | 文面の例 | 表示時間 | 重複の防ぎ方 |
| --- | --- | --- | --- |
| 利用枠が80%を超えた | 5時間枠が81%になりました。18:40 に回復します。 | 8秒 | 枠ごと・回復時刻ごとに1回（`$.store`） |
| 利用枠が95%を超えた | 5時間枠が96%です。まもなく上限です（18:40 回復）。 | 20秒 | 同上 |
| ペースが「速め」に変わった | 5時間枠の消費ペースが速めです。このままだと17:55頃に上限です。 | 10秒 | 同上 |
| コンテキストが40%を超えた | 文脈が40%を超えました。 | 6秒 | 段階ごとに1回（`$.state`） |
| コンテキストが50%を超えた | 文脈が50%を超えました。/compact か /clear を検討する頃合いです。 | 10秒 | 同上 |
| コンテキストが60%を超えた | 文脈が60%を超えました。区切りのよいところで /compact か /clear をおすすめします。 | 15秒 | 同上 |

- **95% のときの OS 通知**：トーストに加えて、`$.ui.notify` で OS の通知も送ります。ただしデスクトップアプリでは OS 通知を送れない（`no-surface` が返る）仕様なので、届くのはターミナルで使っている場合だけです。デスクトップアプリでは、長めのトーストと、ステータス行の `⚠` で代わりにします。
- **利用枠の通知済み記録**：`$.store` に枠の種類ごとに `{ resetsAt, level, isFastNotified }` として保存します。セッションをまたいで残り、mod を再読み込みしても消えません。`resetsAt` が変わったら（＝枠が回復したら）記録をリセットします。回復時刻の秒単位の揺れで記録が外れないよう、10分単位に丸めて比べます。
- **一度に複数の段階を越えたとき**：通知は、越えたうちのいちばん上の段階について1回だけ出します。たとえば一度に 70%→96% になったら、95% の通知だけを出します。
- **コンテキストの通知済み記録**：`$.state` に、通知済みのいちばん上の段階を保存します。`/compact` などで使用率がその段階より5ポイント以上下がったら、現在の値より上の段階をまた通知できる状態に戻します。

## ペース判定

- **5時間枠**：直近30分のサンプル（取得時刻と使用率の組）から傾きを求め、100%に達する予測時刻を出します。
  - 判定に使えるのは、同じ回復時刻のサンプルが2つ以上あり、最初と最後が10分以上離れていて、そのあいだに2ポイント以上増えている場合だけです。
  - **速めになる条件**：予測時刻が回復時刻より10分以上前のとき。
  - **戻る条件**：予測時刻が回復時刻以降になったとき、または判定に使えるサンプルがなくなったとき。差をつけてあるのは、表示がちらつかないようにするためです（ヒステリシス）。
- **週枠**：直近の傾きで判定すると、作業が集中した時間帯にばかり反応してしまいます。そのため枠の始まりからの平均で判定します。
  - 計算式：経過割合 ＝ 1 −（回復までの残り時間 ÷ 7日）
  - **判定する条件**：経過割合が 0.1 以上で、使用率が20%以上のとき。
  - **速めになる条件**：使用率 ÷ 経過割合 が 110% 以上（このまま回復時刻まで続くと上限を超える見込み）。
  - **戻る条件**：100% 未満になったとき。
- **そのほかの枠**：ペース判定はしません。
- **サンプルの保存先**：`$.state`（セッション内）。枠ごとに直近の最大60件まで持ちます。利用枠の使用率はアカウント全体の値なので、どのセッションで集めても結果は同じです。

## パネル

上から次の順に並べます。中身のない項目は出しません。

1. いまの状態（既存のまま）
2. **利用枠**
   ```
   利用枠（18:02 時点）
   5時間 62% ■■■■■■□□□□ 18:40 回復
     ⚠ ペース速め：このままだと 17:55 頃に上限
   週   35% ■■■■□□□□□□ 10/22 回復
   ```
3. **コンテキスト**
   ```
   コンテキスト 45% ■■■■□□□□□□
   約 90k / 200k トークン・次の目安 50%
   1ターンあたり約 +3%・あと 2 ターンほどで 50%
   ```
   - 「1ターンあたり」の増え方は、直近5回の計測（ターン終了ごと）の平均です。増えていないときは出しません。
4. やることリスト（中身があるときだけ出します。今の「まだありません」の行はなくします）

## 対象外（次の段階で作るもの）

- 実行中のサブエージェントの一覧
- 作業ログ（変更したファイル・テスト結果・コミットの時系列）と、`/worklog` による引き継ぎ用の下書き出力

## テスト

`claude plugin test plugins/progress-panel` で確かめます。既存のテストは変えずに通すことに加えて、次の場合を確かめます。

- ステータス行の形（利用枠・コンテキストの有無、`⚠` が付くか、週枠の回復日）
- 80%・95% の通知がそれぞれ1回だけ出るか、一度に越えたら上の段階だけになるか、枠が回復したらまた出せるか
- ペース判定（5時間枠と週枠の両方。条件を満たすとき・満たさないときと、表示のちらつき防止）
- コンテキストの 40%・50%・60% の通知と、使用率が下がったあとにまた通知できる状態に戻るか
- パネルに利用枠・コンテキストが出るか、空のやることリストの行が消えているか（terminal と desktop の両方）
